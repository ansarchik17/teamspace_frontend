# Историческая интеграция бюджета Workspace / AxisMail

Workspace теперь управляет только квотами Drive в MinIO. Поля почтовой доли,
маршруты управления квотами ящиков в Workspace и синхронизация бюджетов удалены.
Вход через Workspace SSO не требует предварительно задавать почтовый бюджет.

Личные почтовые квоты и существующие ограничения AxisMail остаются под управлением
самого AxisMail. Его внутренние маршруты бюджета сохранены для совместимости
с ранее настроенными почтовыми компаниями; Workspace больше их не вызывает.
AXISMAIL_INTERNAL_URL и AXISMAIL_STORAGE_TOKEN больше не нужны бэкенду Workspace
для управления Drive. Существующий токен AxisMail не следует удалять, если его
используют другие внутренние клиенты.

Ниже — описание прежнего контракта, а не инструкция подключения для нового Workspace.

# Общий бюджет компании Workspace / AxisMail

Workspace задаёт общий бюджет и почтовую долю. Drive получает остаток.
Полный публичный контракт для фронта находится в backend:
`docs/company-administration-storage.md`, раздел «Единый бюджет Drive + AxisMail».
Интерфейс AxisMail использует существующий API квот ящиков. Новый внутренний
API предназначен только для сервера Workspace.

В `.env.production` AxisMail задайте:

```dotenv
MAIL_MODE=stalwart
AXISMAIL_STORAGE_TOKEN=<общий случайный секрет не менее 32 символов>
```

Также необходимы существующие `STALWART_URL` и `STALWART_API_KEY_FILE`
(или `STALWART_ADMIN_FILE`). В Workspace задайте тот же секрет и
`AXISMAIL_INTERNAL_URL` — адрес AxisMail, доступный из контейнера Workspace.
Не включайте секрет в `VITE_*`, логи или ответы браузеру.

Обновите оба сервера и примените их миграции. Workspace использует миграцию
`20261013000100_company_shared_storage.sql`, AxisMail — штатный `npm run db:migrate`.
Компания идентифицируется неизменяемым UUID Workspace. После настройки секрета, до первого входа через
Workspace SSO администратор платформы должен установить её почтовую долю;
автоматическое выделение 1 TB отключено. До настройки интеграции сохраняется
прежнее поведение Workspace SSO для совместимого развёртывания. Сначала
сохраните почтовые бюджеты в Workspace и дождитесь синхронизации, затем
включайте новые входы: существующие компании должны иметь настроенные доли.

Внутренний endpoint:
`GET/PUT /api/internal/workspace/organizations/:organization_id/storage`.
Авторизация: `Authorization: Bearer AXISMAIL_STORAGE_TOKEN`.

Персональные квоты директор и администратор платформы редактируют рядом с
Drive в разделе «Квоты» Workspace. Для этого используются серверные маршруты
`GET /api/internal/workspace/organizations/:organization_id/mailboxes`
и `PUT /api/internal/workspace/organizations/:organization_id/mailboxes/:mailbox_id`.
Авторизация — тот же AXISMAIL_STORAGE_TOKEN; браузеру эти маршруты недоступны.
GET принимает limit/offset и возвращает безопасные поля ящиков, общий бюджет,
занятое место, выделенные квоты и revision. PUT принимает quota_bytes (целые
МиБ, минимум 1 МиБ), revision и проверенный Workspace actor_id.
После сохранения revision увеличивается; устаревшие формы получают 409.
При недоступности связи перед повторным сохранением нужно перечитать состояние:
изменение в AxisMail могло сохраниться до разрыва соединения.

При расчёте выделенного объёма для каждого ящика резервируется максимум
сохранённой и применённой в Stalwart квоты. Изменения сериализуются с
провижинингом; при занятости операции возвращают MAIL_BUSY и допускают повтор.
Уменьшение ниже фактически занятого объёма возвращает MAIL_QUOTA_USED (409).
Сохранение запроса и безопасных снимков аудита member.updated атомарно в БД
AxisMail. Изменение применяется фоновым обработчиком; quota_pending в списке
сотрудников показывает ожидание применения. Для выпуска обновляются оба UI.
PUT: `quota_bytes` (почтовая доля в байтах), `revision` AxisMail.
Ответ: `quota_bytes`, `allocated_bytes`, `used_bytes`, `revision`.
Конфликт версии, недостаточный бюджет или неуправляемые ящики возвращают 409.

Сумма всех квот ящиков, включая заблокированные, ограничивается почтовой долей
триггером PostgreSQL. Перед применением индивидуальной квоты дополнительно
проверяются фактические ограничения всех ящиков Stalwart: нельзя увеличить
один ящик, пока уменьшение другого не подтверждено сервером. Для каждого
управляемого ящика устанавливается `quotas/maxDiskQuota`; входящая SMTP-почта
ограничивается Stalwart. Неизвестные аккаунты домена и внешние связанные ящики
не позволяют активировать общий бюджет до их миграции в управляемые.

При увеличении доли Workspace сначала резервирует место, затем повторяет
синхронизацию каждые 10 секунд. При уменьшении сначала подтверждается лимит
AxisMail, затем место передаётся Drive. Фоновый процесс восстановится после
перезапуска или недоступности AxisMail. Почтовое хранилище не переносится
автоматически в MinIO; физическую ёмкость отдельного диска Stalwart необходимо
контролировать отдельно.

Перед production проверить доставку SMTP при заполнении реального ящика.
Автотесты используют изолированную PostgreSQL и имитацию Stalwart API.
