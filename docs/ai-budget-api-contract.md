# API бюджетов и лимитов ИИ

Последний запрос: при положительном остатке, которого не хватило для запроса, сервер может принять сообщение и вернуть HTTP 200 с `object="chat.quota_stop"`, `finish_reason="quota_exhausted"` и обычным assistant-текстом о лимите. В `quota_stop` передаются `scope`, строковая сумма `consumed_microcredits` и `resets_at`. Ввод очищается, сообщение остаётся в истории, лимиты инвалидируются как после успешного ответа. Это завершённый ход, а не `pre_call_rejection`; автоматическая повторная генерация не требуется. Личный used_microcredits учитывает такое расходование остатка квоты отдельно от реального provider usage/token counters.

Актуализация 22 октября 2026: личные запросы ограничиваются только Q и H, `effectiveFiveHour=min(H,Q)`. Отсутствующие настройки используют 250 кредитов / 5 часов и 1500 / 7 дней; явный ноль сохраняет отключение. Корпоративный бюджет и Hmax не блокируют личные запросы и изменение квот. set_user_quotas доступно директору/суперадмину при активной компании без требования бюджета. Личная revision остаётся обязательной, company_revision сохраняется в DTO для совместимости и не ограничивает запись. Оба периода стартуют с первого принятого запроса. Разделы ниже с распределением корпоративного бюджета описывают прежнюю модель; служебные вызовы продолжают использовать общий бюджет.

Дата: 16 октября 2026 года. Задача 04. Версия проекта контракта: 1.

**Статус реализации на 19 октября 2026 года:** в задаче 14 подключены административные маршруты бюджета, списка/одной квоты и изменения настроек. ## 2. Общие правила протокола

- Bearer JWT, HTTPS; язык по существующей политике `Accept-Language`/профиля, ru/kk. GET: `Cache-Control: no-store`. PUT: JSON, предел тела 4 KiB, неизвестные/дублирующиеся поля отклоняются.
- Ответы — JSON-объекты без новой success-обёртки. Успешные PUT: `204 No Content`; затем клиент обновляет GET. Тело ошибки — существующий envelope раздела 8.
- **Все суммы в µcr и все revision передаются строками** из десятичных цифр: `"0"` либо `[1-9][0-9]*`. JSON number, знак, пробелы, экспонента и дробь запрещены. `null` допускается только там, где это явно указано. `1 кредит = 1000000 µcr`.
- Лимит отдельной настраиваемой суммы: `0..1000000000000000` µcr включительно (1 млрд кредитов). Это предлагаемый технический предел контракта, не размер тарифа. Расход, резервы и агрегаты — неотрицательные int64, могут превышать установленный лимит при выявленном перерасходе; checked arithmetic обязательна. Revision — неотрицательный int64, без циклического переполнения.
- UUID компаний/периодов — строки; существующие `user_id` сохраняют целочисленный формат существующего API пользователей. `limit`, `offset`, `total` — JSON integer. Проценты — integer 0–100 либо null.
- Время — RFC3339 UTC с `Z`; интервалы `[starts_at, ends_at)`. `server_time` — момент согласованного снимка. Нулевые/неоткрытые периоды не создаются от GET.
- Ни один клиентский запрос не задаёт расход, остаток, окно, фактическую компанию попытки или версию цен. Всё это определяет сервер.
- Административные GET дают согласованный снимок внутри одного ответа. Отдельные страницы списка и отдельные запросы не являются общей транзакцией; клиент обновляет сводку после изменений.

## 3. Общие объекты

### Period

`null`, если якорь ещё не открыт, иначе:

```json
{"id":"4bdeec70-7294-4c1c-96a7-f49109329981","starts_at":"2026-10-16T05:00:00Z","ends_at":"2026-10-23T05:00:00Z"}
```

`id` — непрозрачный стабильный идентификатор сохранённого периода, не revision. Уточнение задачи 14: для вычисленного окна, которое ещё не создано успешным резервированием, `id=null`, а starts_at/ends_at заданы. После простоя GET возвращает актуальное окно постоянной сетки без записи в БД, не сдвигая якорь. Сам объект period=null только при отсутствии якоря.

### LimitWindow

```json
{
  "state":"active",
  "limit_microcredits":"100000000",
  "used_microcredits":"30000000",
  "reserved_microcredits":"20000000",
  "carried_reserved_microcredits":"5000000",
  "available_microcredits":"50000000",
  "remaining_percent":50,
  "period":null
}
```

Поля примера иллюстрируют типы; `period` может быть null при перенесённых резервах до открытия нового якоря. Для уже начавшегося расхода текущего окна period обязательно задан; фактический ответ не должен иметь used>0 с period=null.

- `state`: `unconfigured`, `disabled`, `active`, `exhausted`.
- `limit_microcredits=null` и available/percent=null только для unconfigured. Счётчики даже в этом состоянии показывают известные значения, не стираются.
- disabled: эффективный лимит 0, available=0, percent=null. exhausted: положительный лимит, available=0. active: положительный остаток, но его может не хватить на конкретный резерв.
- `reserved_microcredits` — всё удержание этого ограничения, **включая** carried; carried — его часть из ранее начатых периодов. Не складывать эти два поля повторно.
- available=`max(0,limit−used−reserved)`; процент округляется вниз. При положительном available и percent=0 интерфейс показывает «меньше 1%».
- Для H используется эффективный `min(H,Q,Hmax)`; used пятичасового окна относится к userID и может включать прежнюю компанию. Для недельной квоты used относится только к этой компании и её периоду.

## 4. Собственные лимиты

`GET /api/v1/ai/limits`, 200:

```json
{
  "server_time":"2026-10-16T06:00:00Z",
  "organization_id":"f4673508-34cb-4dc7-9c17-f664271eb50f",
  "enforcement_mode":"enforced",
  "credit_policy_version":"credits-v1",
  "five_hour":{"state":"active","limit_microcredits":"100000000","used_microcredits":"30000000","reserved_microcredits":"0","carried_reserved_microcredits":"0","available_microcredits":"70000000","remaining_percent":70,"period":{"id":"32ef21c9-155e-42f8-a2de-2be807ba072e","starts_at":"2026-10-16T05:20:00Z","ends_at":"2026-10-16T10:20:00Z"}},
  "weekly":{"state":"active","limit_microcredits":"1000000000","used_microcredits":"30000000","reserved_microcredits":"0","carried_reserved_microcredits":"0","available_microcredits":"970000000","remaining_percent":97,"period":{"id":"4bdeec70-7294-4c1c-96a7-f49109329981","starts_at":"2026-10-16T05:00:00Z","ends_at":"2026-10-23T05:00:00Z"}},
  "access":{"can_start_request":true,"blockers":[],"retry_at":null,"retry_kind":"none","recheck_at":null}
}
```

`organization_id=null` для пользователя без компании: 200 со состоянием настройки, blocker `NO_ORGANIZATION`, доступ закрыт. `credit_policy_version=null`, если активной политики нет. `enforcement_mode`: `observe` или `enforced`; изменяется серверной конфигурацией, а не этим API. observe не отменяет запрет по правам/блокировке; квотные причины показываются с `enforced:false`.

`can_start_request=true` означает отсутствие известного общего запрета, **не гарантию** принятия любого размера/модели запроса. Реальное резервирование проверяется отдельно. Никаких корпоративных сумм и данных коллег в этом ответе нет.

Blocker — объект `{reason, scope, enforced, resets_at}`. scope: `account`, `company`, `weekly`, `five_hour`, `policy`. resets_at — граница соответствующего периода либо null. Для компании сотруднику допускается показать границу обновления без суммы бюджета.

Причины: `NO_ORGANIZATION`, `COMPANY_SUSPENDED`, `AI_ACCESS_DENIED`, `COMPANY_BUDGET_UNCONFIGURED`, `USER_QUOTA_UNCONFIGURED`, `COMPANY_BUDGET_DISABLED`, `USER_QUOTA_DISABLED`, `FIVE_HOUR_DISABLED`, `COMPANY_WEEKLY_EXHAUSTED`, `USER_WEEKLY_EXHAUSTED`, `FIVE_HOUR_EXHAUSTED`, `RESERVATION_PENDING`, `CREDIT_POLICY_UNAVAILABLE`. Не возвращать чужие суммы или provider diagnostics. Блокировка аккаунта обычно отклоняется middleware до этого ответа: 401/403 по существующему контракту.

## 5. Бюджет компании

`GET D/ai-budget` либо P, 200. Поля:

| Поле | Тип / смысл |
| --- | --- |
| `organization_id`, `server_time`, `enforcement_mode` | Как выше; компания обязательна |
| `revision` | Версия конфигурации B/Hmax/Qservice; `"0"` для ещё не настроенной |
| `configured` | boolean; false до первого успешного PUT |
| `weekly_budget_microcredits` | B, string/null |
| `max_five_hour_microcredits` | Hmax, string/null |
| `service_weekly_quota_microcredits` | Qservice, string; начальное `"0"` |
| `period` | Недельный Period/null |
| `employee_allocated_microcredits` | Сумма текущих Q сотрудников |
| `allocated_microcredits` | Сумма Q сотрудников + Qservice |
| `committed_microcredits` | Σ max(Qi,Si+Ri), включая служебное выделение и бывших сотрудников |
| `used_microcredits`, `reserved_microcredits`, `carried_reserved_microcredits` | Общие счётчики компании; carried входит в reserved |
| `unallocated_microcredits` | max(0,B−committed), null если B не настроен |
| `available_microcredits` | max(0,B−used−reserved), null без B |
| `overcommitted_microcredits` | max(0,committed−B), null без B |
| `remaining_percent` | Процент доступного B; null без B либо при B=0 |
| `service` | Объект с `used_microcredits`, `reserved_microcredits`, `carried_reserved_microcredits`, `available_microcredits`; available=max(0,Qservice−used−reserved) |
| `capabilities` | `{set_company_budget:boolean,set_service_quota:boolean,set_user_quotas:boolean}` |

Директор: первые две capabilities false; set_user_quotas только при активной компании и настроенном бюджете. Платформа имеет первые две true, личные назначения для suspended-компании запрещены, как и директору. Платформа может читать suspended и изменять B/Hmax/Qservice, в том числе B=0. Право не заменяет бизнес-проверку.

В реализации задачи 14 enforcement_mode возвращается как observe: ограничения ещё не подключены к провайдерам. Полноценный режим наблюдения за всеми платными путями и переключатель enforcement относятся к следующим задачам; этот ответ не утверждает, что расход всех провайдеров уже собирается. Клиент не может изменить режим через PUT бюджета.

`PUT P/ai-budget`, все поля обязательны:

```json
{"weekly_budget_microcredits":"1000000000","max_five_hour_microcredits":"100000000","service_weekly_quota_microcredits":"100000000","revision":"0"}
```

Первый PUT создаёт настройки; null для снятия настройки запрещён. Ноль — явное отключение, не unlimited. Изменение атомарное: проверяются итоговые обязательства с новым Qservice. Положительный B не может быть ниже committed. B=0 разрешён как аварийное отключение; существующие выделения/расход/резервы сохраняются, но увеличивать Qservice одновременно запрещено. Снижение Hmax не переписывает H сотрудников: меняется эффективный лимит. Успех — аудит `ai.budget.update` и увеличение revision в одной транзакции; названия событий новые.

## 6. Квоты сотрудников и пагинация

GET `/ai-budget/users?limit=25&offset=0&q=...` относительно D/P:

```json
{"items":[],"total":0,"limit":25,"offset":0,"server_time":"2026-10-16T06:00:00Z","company_revision":"1","period":null}
```

limit=1..100, default 25; offset≥0, default 0, максимум 2147483647; q≤255 Unicode-символов после trim, пустой эквивалентен отсутствию. Поиск по ФИО/username/email в пределах компании, `%` и `_` — обычные символы. Стабильная сортировка user_id ASC. total — число подходящих текущих неудалённых сотрудников, включая неактивных, директора и заблокированных; offset за концом даёт пустой items. Переведённые/удалённые не возвращаются, но их расход сохраняется в сводке. Обязательства компании поэтому могут не совпасть с суммой видимых строк.

Поля назначения UserQuota (фрагмент ответа GET `/users/:user_id`; обязательные объекты окон описаны ниже):

```json
{
  "user_id":123,"full_name":"Сотрудник","username":"employee","email":"employee@example.com",
  "is_active":true,"is_blocked":false,"is_director":false,
  "configured":true,"revision":"2","company_revision":"1",
  "weekly_quota_microcredits":"500000000",
  "five_hour_limit_microcredits":"100000000",
  "effective_five_hour_microcredits":"100000000",
  "committed_microcredits":"500000000",
  "server_time":"2026-10-16T06:00:00Z"
}
```

Полный UserQuota дополнительно обязательно содержит `weekly` и `five_hour` — объекты LimitWindow, не null. Для неназначенной квоты configured=false, Q/H=null; effective=null, committed учитывает сохранившийся расход/резервы. Revision="0" только если запись назначения ещё никогда не создавалась; восстановление не обнуляет версию. Эффективный доступ при отсутствии назначения закрыт. В поле five_hour администратор новой компании видит общий счётчик пользователя, без расшифровки прежней компании и её операций. Каждый item списка имеет ту же схему UserQuota.

`PUT /ai-budget/users/:user_id` относительно D/P:

```json
{"weekly_quota_microcredits":"500000000","five_hour_limit_microcredits":"100000000","revision":"2","company_revision":"1"}
```

Все поля обязательны. Проверка назначений: H≤Q и H≤Hmax при создании/увеличении H. При снижении Q разрешается сохранить прежнее H выше Q; эффективный H ограничивается минимумом. Аналогично уже сохранённое H после снижения Hmax не требует немедленного переписывания. Это позволяет снизить Q до 0 без принудительной потери настройки H. Новый ненулевой H при Q=0 запрещён. Не назначать квоту при ненастроенной компании.

Новое назначение должно поместиться в итоговое committed. Если компания уже overcommitted (например B=0 или обнаруженный перерасход), допускается только изменение, не увеличивающее Q/H и обязательство сотрудника. Оно не обязано сразу устранить всё превышение. Успех — аудит `ai.user_quota.update`, 204. Пакетного PUT в версии 1 нет: перераспределение «сначала уменьшить, затем увеличить». Каждый запрос атомарный; серия запросов не является транзакцией. При частичном успехе клиент обновляет данные, не повторяет всю серию автоматически.

## 7. Revision и конкуренция

- company revision меняется только при изменении B/Hmax/Qservice; расходы, новые периоды и изменения Q сотрудников её не увеличивают.
- user revision меняется при изменении назначения, его освобождении при увольнении/переводе и повторном назначении; потребление и смена окна её не меняют. Возвращённый в компанию сотрудник не получает повторно старый revision=0: хранить монотонную версию записи, чтобы исключить ABA.
- PUT пользователя проверяет обе версии. Они защищают настройки, но не обещают неизменность свободного бюджета. Все расход/резервы/принадлежность и итоговые суммы повторно проверяются в транзакции.
- Успешное создание с revision="0" даёт "1"; дальнейшие реальные изменения +1. PUT с актуальными версиями и идентичными значениями — 204 без нового аудита/версии. Проверка версий предшествует сравнению: повтор после потерянного ответа может получить 409, тогда выполнить GET.
- При 409 клиент сохраняет ввод, перечитывает GET и предлагает повторить изменение с актуальными данными. Автоматический retry с подменой revision запрещён.
- Переход периода сам не конфликт версии: PUT применяется к актуальному периоду на момент транзакции; UI показывает обновлённую сводку. Никакого обещания зарезервировать доступный остаток через GET нет.

| HTTP / code | Когда |
| --- | --- |
| 400 `VALIDATION_ERROR` (существующий) | Неверный JSON, значение/диапазон/пагинация/идентификатор |
| 401 `UNAUTHORIZED`, 403 `FORBIDDEN` (существующие) | Нет аутентификации/прав, заблокированный аккаунт по текущему middleware |

| 409 `AI_REVISION_CONFLICT` (новый) | Не совпали company/user revision |
| 409 `AI_BUDGET_CONFLICT` (новый) | Назначения не помещаются; B ниже обязательств; попытка увеличить квоту при превышении |
| 409 `AI_CONFIGURATION_REQUIRED` (новый) | Административное назначение до настройки бюджета |
| 409 `AI_COMPANY_SUSPENDED` (новый) | Запрещённое изменение личной квоты suspended-компании |
| 403 `AI_ACCESS_DISABLED` (новый) | Платная операция запрещена отсутствующей/нулевой настройкой, статусом компании или правом доступа |
| 429 `AI_QUOTA_EXCEEDED` (новый) | Конкретный резерв не помещается в один или несколько лимитов |
| 429 `TOO_MANY_REQUESTS` (существующий) | Ограничение частоты/параллельности, не токенный бюджет |
| 503 `AI_ACCOUNTING_UNAVAILABLE` (новый) | Нельзя безопасно проверить/записать резерв или отсутствует политика |
| 503 `AI_MODEL_UNPRICED` (новый) | Нет активного профиля запрошенной модели/операции |
| 500 `INTERNAL_ERROR` (существующий) | Непредвиденная серверная ошибка без раскрытия деталей |

Первые административные ошибки применяются к новым PUT. Ошибки платных операций добавляются при подключении учёта к существующим AI endpoint; формат успешных ответов этих endpoint этим документом не меняется. Старую ошибку провайдера HTTP 429 нельзя превращать в AI_QUOTA_EXCEEDED: это разные причины.

```json
{"error":{"code":"AI_REVISION_CONFLICT","message":"Настройки изменились. Обновите данные.","user_message":"Настройки изменились. Обновите данные.","details":{"scope":"user","expected_revision":"2","current_revision":"3"}}}
```

Allowlist новых details по коду:

- AI_REVISION_CONFLICT: scope=`company|user`, expected_revision/current_revision — строки. При конфликте обеих версий сначала company; не включать чужие данные.
- AI_BUDGET_CONFLICT: reason=`INSUFFICIENT_BUDGET|BUDGET_BELOW_COMMITTED|INCREASE_WHILE_OVERCOMMITTED`, available_microcredits/required_microcredits/committed_microcredits — строки, только уполномоченному администратору.
- AI_CONFIGURATION_REQUIRED/AI_ACCESS_DISABLED/AI_COMPANY_SUSPENDED: reason из безопасного перечня раздела 4, без сумм компании. Для административного suspended reason=COMPANY_SUSPENDED.
- AI_QUOTA_EXCEEDED: blockers, retry_at, retry_kind, recheck_at, server_time. Дополнительный reason внутри blocker `RESERVATION_TOO_LARGE` обозначает положительный остаток, недостаточный для запроса; scope указывает ограничение. Корпоративные суммы и индивидуальные данные коллег не выдавать.
- AI_ACCOUNTING_UNAVAILABLE/AI_MODEL_UNPRICED: безопасное сообщение без сырых моделей провайдера, URL, ключей, SQL и диагностических ответов.

Валидация использует существующие локализованные field tags, а не произвольный диагностический reason. Все новые коды должны быть зарегистрированы в SafeCode/локализации; существующие коды и сообщения для диска не изменяются.

## 9. Время повторного доступа

Объект access и ошибка квоты используют одинаковую семантику:

- `retry_kind=none`, retry_at=null: сейчас нет квотного запрета.
- `retry_kind=estimated`, retry_at=timestamp: при текущих настройках все блокирующие временные лимиты ожидаемо восстановятся к этому моменту; берётся максимум их ends_at.
- `retry_kind=requires_action`, retry_at=null: требуется назначение/повышение квоты, активация компании, исправление политики или иной нетаймерный шаг.
- `retry_kind=unknown`, retry_at=null: восстановление зависит от сверки незавершённых резервов, размер/эффект которой неизвестен.

requires_action имеет приоритет над unknown, затем estimated. Если размер конкретного резерва больше полного лимита даже нового периода, это requires_action, а не обещание восстановления на границе. Состояние платежеспособности GET без параметров запроса и отказ конкретного большого запроса могут поэтому иметь разные причины.

`recheck_at` — подсказка времени следующего GET, а не разрешение автоматически повторить генерацию. При estimated равно retry_at; при unknown сервер может дать момент следующей проверки сверки; в остальных случаях null. В blockers всегда можно показать известные resets_at независимо от итогового retry_kind.

`Retry-After` в ошибке 429 AI_QUOTA_EXCEEDED возвращать только при estimated: целые секунды `ceil((retry_at−server_time)/1с)`, минимум 1. При unknown/requires_action не задавать фиктивную задержку. Повтор требует актуальной серверной проверки и не гарантирован из-за возможных изменений квот и резервов.

## 10. Совместимость и проверки реализации

В версии 1 не добавляются публичные операции ручного списания, закрытия неизвестного usage, смены политики коэффициентов или режима observe/enforced. Это доверенные внутренние сценарии с отдельным аудитом. Новые capabilities возвращаются в ai-budget и не переопределяют существующее `set_company_quota` дискового раздела. Изменение administration overview при необходимости — отдельное явно документированное дополнение.

Проверки реализации: роли и межкорпоративная изоляция; отсутствие настройки/0; строковые int64 и overflow; согласованность снимка; стабильная пагинация; обе revision и потерянный ответ PUT; независимость revision от расхода; конкуренция распределения и резервов; смена периода/компании; аудит с откатом; переносимые резервы; корректный Retry-After; локализация ru/kk и фильтрация details. Во фронтенде — обработка ошибок без потери ввода, отмена устаревшего GET, запрет дублирования сохранения.

Первоначальная задача 04 меняла только документацию. В задачах 05–14 добавлены миграции и серверные операции; административные маршруты/DTO подключены в задаче 14. Проверки квот при вызове провайдера, личные лимиты и остальная интеграция остаются будущими задачами. Перед использованием административного API требуется обновить бэкенд и применить миграции 05–07; клиентский интерфейс будет подключён отдельно. Подробности проверок — `workspace-backend/docs/ai-administration-http.md`. Задача 14 не выполняет commit, push или развёртывание.
