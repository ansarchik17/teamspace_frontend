Основания: [инвентаризация вызовов](ai-provider-call-inventory.md), [утверждённые правила бюджетов R1–R6](ai-budget-period-rules.md).

**Статус: согласовано пользователем 16 октября 2026 года.** Утверждены начальные веса и классы моделей раздела 4, а также назначение Qservice платформой с начальным значением 0. Это внутренняя продуктовая шкала, не подтверждённые тарифы провайдеров. Проверка контрактов usage остаётся обязательным условием активации соответствующих путей. Код и текущие API этим документом не изменяются.

## 1. Что измеряет кредит

ИИ-кредит — внутренняя единица потребления, основанная на подтверждённом расходе провайдера. Это не валюта и не точное отражение счёта провайдера. Кредиты разных запросов суммируются в бюджет компании, недельную квоту и пятичасовой лимит пользователя по R1–R6.

Данные токенов и рассчитанные кредиты хранятся раздельно. Недостаточный лимит не уменьшает сохранённый реальный расход. Сумма входных токенов включает весь отправленный контекст, а не только последнее сообщение пользователя. Размер текста в символах, байтах или словах не заменяет usage провайдера при окончательном списании.

Используется минимальная единица **микрокредит (µcr)**: `1 кредит = 1 000 000 µcr`. Все лимиты, резервы и списания в хранилище и API учёта выражаются целыми µcr. Показываемое пользователю значение кредита — форматирование целого числа, а не float. Это уточняет термин «целые кредиты» из задачи 02: целочисленной единицей хранения является µcr.

| Путь | Категории, моделируемые текущим кодом | Ограничения |

## 3. Нормализованный расход

Для каждой фактической попытки хранить nullable неотрицательные целые значения:

- `input_tokens` — общий вход;
- `output_tokens` — общий выход;
- `total_tokens` — контрольное значение провайдера, **не третья списываемая категория**;
- `cached_input_tokens` — часть input, только если явно подтверждена адаптером;
- `reasoning_output_tokens` — часть output, только если явно подтверждена адаптером;
- источник usage, статус проверки, версия адаптера и идентификатор ответа провайдера, если он есть.

`null` означает неизвестно/не прислано, `0` — явно переданный ноль. Текущих Go-полей типа int недостаточно для различения этих случаев; будущий адаптер должен проверять присутствие полей при декодировании до потери информации.

Требования:

1. Отрицательные, дробные, строковые вместо чисел и переполняющие значения отклоняются как некорректный usage; нулём не заменяются.
2. Для completions нужны input и output. Если присутствуют total и только одна из двух категорий, вторую можно вывести вычитанием **только в профиле адаптера, подтверждающем `total=input+output`**. Записывается признак derived. Только total для completions недостаточно при разных весах input/output.
3. При наличии всех трёх полей адаптер проверяет равенство, если его контракт его требует. Несогласованность переводит попытку на сверку; не выбирать молча удобное поле.
4. Для embeddings/rerank total допустимо трактовать как input только после подтверждения семантики конкретного provider/model/endpoint. Иначе расход неизвестен.
5. Cached/reasoning используются как подмножества только при подтверждённой семантике: `cached ≤ input`, `reasoning ≤ output`. Они не прибавляются поверх исходных totals. Если детали не присланы, используется профиль без скидок/надбавок: весь input/output по базовым весам.
6. Различать reported-zero и подтверждённый нулевой расход. Нулевой usage при непустом ответе модели требует сверки, если контракт явно не допускает такую ситуацию. Пустой ответ или HTTP-ошибка также не доказывают нулевой расход.
7. Дополнительные категории audio/image/cache-write и других единиц не поддерживаются автоматически. Если они уже включены в input/output по подтверждённому контракту, отдельного списания нет. Если требуют самостоятельного учёта — новый профиль и версия схемы; до этого такой режим не разрешается в жёстком контроле.

## 5. Формула и округление

Базовый профиль без отдельных категорий:

```text
charge_microcredits = input_tokens × input_weight + output_tokens × output_weight
```

Профиль с подтверждёнными подмножествами:

```text
regular_input  = input_tokens − cached_input_tokens
regular_output = output_tokens − reasoning_output_tokens
charge = regular_input × w_input + cached_input_tokens × w_cached
       + regular_output × w_output + reasoning_output_tokens × w_reasoning
```

Начальные `w_cached=w_input`, `w_reasoning=w_output`: обе формулы дают одинаковый результат. Embeddings/rerank с подтверждённым token-input профилем: `charge=input_tokens × w_input`.

Веса — целые µcr за единицу. Дробные веса запрещены: если требуется точность менее 1 µcr на единицу, текущая шкала её не поддерживает; нужно отдельное изменение масштаба/версии, а не скрытый float. Все умножения, вычитания и сложения проверяются на переполнение signed int64. Ограничения счётчиков и весов проверяются до вычисления произведения.

**Окончательное списание в µcr не округляется**, так как результат уже целый. Нет округления каждого вызова вверх до целого кредита и нет минимального списания в один кредит. Отображение допускает дробную часть через деление и остаток целых чисел; оно не меняет баланс. Проценты отображаются по правилам задачи 02.

Бюджеты в формах можно вводить с точностью до 6 десятичных знаков кредита. Разбирать строку в целые µcr, без `parseFloat` и умножения float. Числа больше безопасного целого JavaScript передавать как десятичные строки; окончательную схему полей закрепить в задаче 04. В JSON провайдера значения счётчиков также декодировать без промежуточного float64.

## 6. Версионирование и воспроизводимость

- Политика — неизменяемая опубликованная версия с датой вступления в силу, точными ключами моделей, весами, профилями usage и единицами. Черновик не используется для списания.
- Версия закрепляется при резервировании каждой фактической попытки. Новая версия применяется к новым попыткам после активации; уже зарезервированная попытка завершается по своей версии.
- В журнале сохраняются версия политики и адаптера, запрошенная/подтверждённая модель, исходные числовые категории, нормализованные категории, веса и итог в µcr. Для воспроизведения не требуется хранить текст промпта или секреты.
- Смена коэффициентов не пересчитывает прошлый расход, не меняет численные бюджеты и не перезапускает периоды. Покупательная способность оставшихся кредитов может измениться; изменение публикуется заранее. Для плановых изменений предпочтительна активация между периодами, но она задаётся единым серверным моментом и не меняет якоря компаний.
- Исправление ошибочного учёта оформляется отдельной корректирующей записью со ссылкой на исходную попытку, причиной и аудитом; исходная запись не переписывается. Поздний usage рассчитывается по первоначально закреплённой политике.
- Повторная обработка одного provider response не списывает повторно. Однако одинаковое содержание запроса не означает одну попытку: фактически выполненные retries/fallback учитываются отдельно.

## 7. Резерв и выбор модели

Резерв и окончательный расход различаются. Резерв использует профиль модели, оценку входа с учётом полного контекста и верхнюю границу выхода. Обязателен ограниченный output budget и проверенный способ ограничения входа. Токенизатор/оценщик определяется адаптером; без доказанной верхней границы нельзя обещать невозможность превышения.

Неизвестная модель до отправки: вызов запрещён в режиме ограничений; никакого коэффициента по умолчанию или бесплатного обхода. Можно выбрать только явно разрешённую альтернативу и создать для неё новую попытку и резерв. В наблюдении вызов допустим при существующем разрешении приложения, но расход помечается unpriced, а не 0.

Если provider response содержит иной model ID, он должен совпасть с зарегистрированным разрешённым alias/профилем. Неизвестный ID после выполнения переводит операцию на сверку с удержанием резерва. Для не возвращающего модель endpoint допускается идентификация по запросу только при зафиксированной гарантии его адаптера. Если достоверно установлен расход другой известной модели, расчёт выполняется по её записи той же закреплённой версии с фиксацией расхождения.

Fallback — новая фактическая попытка по весам новой модели. Ошибочный первый ответ не освобождает старый резерв автоматически. Если он подтверждённо бесплатен, его резерв освобождается; если результат неизвестен, удерживается. Перед повтором нужна новая проверка достаточности всех бюджетов.

## 8. Отсутствующий и недостоверный usage

| Состояние | Действие |
| --- | --- |
| Полный валидный usage | Точное списание, освобождение остатка резерва |
| Частичный, но выводимый по подтверждённому контракту | Нормализация с признаком derived, затем точное списание |
| Нет usage, только total без допустимого разложения, некорректные значения или расхождение | Статус unknown/needs-reconciliation, резерв удерживается |
| Подтверждённый отказ до выполнения у провайдера | Подтверждённый расход 0, резерв освобождается |
| Таймаут, отмена, HTTP 5xx/429 без гарантии неисполнения, обрыв потока | Результат неизвестен; не назначать нулевой расход по одному коду HTTP |

Сначала сверять по стабильному provider request ID/usage API, если такой контракт доступен. Для SSE нужен финальный usage и идентификатор попытки; отсутствие финального чанка требует сверки. Сумма usage частичных сообщений допустима только при подтверждении, что они дельты, а не накопительные значения.

Если автоматическая сверка невозможна, требуется ручное закрытие уполномоченным оператором по доказательствам: подтвердить расход, подтвердить неисполнение либо явно оформить списание неизвестного расхода за счёт платформы и освободить резерв. Последний случай не записывать как известные нулевые токены. Срок сверки — эксплуатационная настройка; истечение срока само по себе не доказывает бесплатность. Поиск по локальному тексту и приблизительный токенизатор не создают «реальный usage» задним числом.

## 9. Служебное выделение и нетокенные услуги

По R6 вводится Qservice — отдельное недельное выделение внутри B для общей индексации Drive. Его задаёт платформа, директор распределяет оставшийся бюджет сотрудникам. Qservice по умолчанию 0; положительное выделение требует явной настройки. Оно использует недельные границы компании, входит в сумму обязательств как `max(Qservice, Sservice+Rservice)` и не получает личный пятичасовой лимит. При исчерпании новая платная индексация откладывается; она не переводится автоматически на квоту случайного сотрудника. Нужна отдельная защита частоты и дедупликация индексации.

Qservice нельзя одновременно учесть как «расход пользователя» и «расход службы». Автозаголовки и платные шаги конкретного ответа остаются за пользователем. On-demand индексация общего файла относится к Qservice, а embedding запроса, rewrite, HyDE и rerank его результатов — к инициатору поиска. При отсутствии достоверной компании фонового задания выполнение откладывается, а не оплачивается из текущей компании владельца постфактум.

STT, 2slides и внешний DocumentParse не получают вымышленные токены. Для них нужна отдельная версия профиля: например, подтверждённые целые миллисекунды аудио или единицы задания, целый вес µcr за эту единицу и идентификатор результата. Это примеры допустимых схем, не установленные контракты провайдеров. До проверки контракта тариф остаётся disabled/unpriced; в режиме жёсткого контроля платный путь не выполняется. Внешние сервисы с несколькими внутренними моделями должны возвращать детализацию или явно согласованную итоговую единицу.

Уточнение к R6 согласовано пользователем 16 октября 2026 года: Qservice назначает платформа, начальное значение — 0; директор распределяет сотрудникам оставшийся бюджет.

## 10. Контрольные примеры

Все примеры используют утверждённые внутренние веса, не реальные цены.

| Случай | Расчёт | Результат |
| --- | --- | --- |
| Базовая модель: input=2000, output=1000 | `2000×1000 + 1000×3000` | 5 000 000 µcr = 5 кредитов |
| Повышенный класс, те же токены | `2000×2000 + 1000×6000` | 10 кредитов |
| Базовая модель: input=1, output=1 | `1000+3000` | 4000 µcr = 0,004 кредита, не 1 кредит |
| Подтверждённый embedding input=1234 | `1234×100` | 123 400 µcr = 0,1234 кредита |
| Input=1000, cached=400; output=200, reasoning=50 | `(600+400)×1000 + (150+50)×3000` | 1,6 кредита; детали не удваивают total |
| Только total=3000 у chat | Нет разложения input/output | Не списывать по предположению; сверка |
| Два отдельных базовых вызова по input=1/output=1 | `4000+4000` | 8000 µcr; не округлять каждый до кредита |
| Резерв 8 кредитов, подтверждено 5 | Списание 5, освобождение 3 | Один расход учитывается во всех применимых ограничениях |
| Резерв 8, usage неизвестен | Точного списания нет | 8 удерживаются, включая переход периода по R5 |

Дополнительные обязательные тесты будущей реализации: присутствие/отсутствие полей, reported-zero, отрицательные/дробные значения, total mismatch, детали больше totals, int64 overflow, неизвестная модель/alias, граница активации политики, поздний usage, идемпотентное закрытие и корректирующие записи.
