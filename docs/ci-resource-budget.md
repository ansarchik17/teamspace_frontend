# Frontend build resource budget

The shared production VPS runs only one CI job at a time. Keep its host admission gate and the existing 1536 MiB hard runner limit, 256 MiB swap limit and 100% CPU quota.

The frontend runner uses `MemoryHigh=1280M`. A 1 GiB soft threshold caused continuous direct reclaim during chunk rendering, memory pressure above 50%, and loss of the runner heartbeat without an OOM kill. The hard limit is unchanged. Persistent server settings are managed by `infrastructure/apply-ci-resource-guard-20261022.py` in the deployment workspace; match the frontend service explicitly.

CI runs the full TypeScript check with a 1024 MiB JavaScript heap, then bundles with a 640 MiB heap. The image builder runs only the bundle with 640 MiB (verified in a 1 GiB container); the required TypeScript gate has already passed before image publication. `npm run build` retains both checks for ordinary development. Both environments set `ROLLDOWN_WORKER_THREADS=1` and `RAYON_NUM_THREADS=1` before startup, leaving room for native Rust allocations and runner control processes. Do not increase all runner limits or run parallel jobs on this host to resolve a failed build.

Rolldown worker configuration: https://rolldown.rs/guide/troubleshooting#containers-and-cpu-emulation

Manual vendor groups retain `strictExecutionOrder: true`: without it a split React CommonJS wrapper could run before initialization, despite a successful build and healthy nginx. Before publishing, CI starts the emitted `dist` in Chromium and checks login, navigation to recovery, and direct invalid recovery/invitation links, rejecting uncaught JavaScript errors. This runs in the official Playwright image matching the exact devDependency, capped at 768 MiB RAM, 256 MiB swap and one CPU, with a private 256 MiB shared-memory segment. The repository is mounted read-only and external networking is disabled; the test uses a local static server and never sends mail or signs in. Run locally after bundling with `npm run test:production-build` (install the matching Chromium first with `npx playwright install chromium --only-shell`).

Chunk execution order: https://rolldown.rs/reference/Interface.OutputOptions#strictexecutionorder

Production builds export each image to both GHCR and the local Docker image store (`push: true`, `load: true`). Build and deploy use the same host, so this avoids downloading newly built layers over the registry route again. Registry publication, normal deployment pulls and health checks remain required. Multiple exporters require Buildx and BuildKit 0.13 or newer: https://docs.docker.com/build/exporters/#multiple-exporters.

The frontend BuildKit container is capped at 2 GiB RAM plus 256 MiB swap, one CPU, and one build vertex at a time. Its separate Excalidraw image needs a 1024 MiB Node heap: cold Linux builds failed at 640/768 MiB and passed at 1024 MiB within a standalone 1536 MiB container. The complete production BuildKit build was then killed at the 1536 MiB limit during chunk rendering; a standalone Node-container test did not include the builder daemon and its other processes. Reserve that overhead in the builder budget, and cap the esbuild Go process with `GOMAXPROCS=1` and a 256 MiB soft Go memory limit. The Node heap remains bounded, minification stays enabled, and `npm ci` uses the committed lockfile. A dedicated `.dockerignore` prevents host dependencies, previous build output and local dotenv files from entering the image build; rehearse the complete image for `linux/amd64`, matching production. The mail image passed its full TypeScript/bundle build at 640 MiB heap in a 1 GiB container and uses that explicit heap cap. The host admission gate still requires 3 GiB available before starting the serialized job; runner and application service limits are unchanged.

The full `linux/amd64` whiteboard image rehearsal with these settings passed at a measured BuildKit cgroup peak of 1,999,372,288 bytes (about 1907 MiB), with `memory.events` reporting zero max-limit hits and zero OOM kills. The resulting image also passed `nginx -t`. Measure the complete builder, not only the Node process, when changing this budget.

The separate whiteboard Keycloak realm also needs a runtime budget in both standalone and shared Compose files: a 64–256 MiB Java heap, a 768 MiB container RAM limit and a 1 GiB RAM-plus-swap limit. Previously its uncapped JVM used `InitialRAMPercentage=50`/`MaxRAMPercentage=70` against the whole VPS, occupying about 837 MiB while only about 49 MiB of live heap remained after GC. That prevented the next CI job from satisfying the unchanged 3 GiB admission gate. Keep this explicit heap when updating the deployment templates.

Use the same job-scoped temporary `DOCKER_CONFIG` for build and deployment. Switching it for the deployment login hid the Buildx metadata from post-job cleanup: the successful job logged `ci-workspace-front does not exist` while its BuildKit container kept running. `setup-buildx-action` must find that metadata to remove the builder with `--keep-state`, stopping its daemon while retaining its cache volume. The admission gate counts at most 128 MiB of the exact current Runner.Worker RSS as an already allocated part of the 3 GiB total CI budget; other processes and swap do not count. PSI and disk checks remain required.
