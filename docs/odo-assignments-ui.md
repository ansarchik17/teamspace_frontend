# Задача 7: поручения ЭДО в разделе «Работа»

Экран использует `GET /api/v1/kanban/documentolog/assignments` и пользовательскую команду `POST /api/v1/kanban/documentolog/assignments/{task UUID}/complete` из задачи 6. Обычный Kanban status endpoint для поручений больше не вызывается.

## Отображение

- Название, описание, приоритет и исходные assignment/document ID берутся из бэкенда. «Открыть в ЭДО» использует существующий маршрут Workspace `/web/eps?document=<encoded source_document_id>` на текущем origin. Он создаёт одноразовый handoff и открывает `/odo/documents/<encoded ID>` в том же тенанте. Общий домен из `source_url` не используется для навигации; токены не добавляются в ссылку. При отсутствии ID документа кнопка скрыта. Доступ к документу проверяет ЭДО.
- Статусы `assigned`, `in_progress`, `completed`, `closed`, `cancelled` отображаются по `source_status`. Канбан-статус не подменяет статус ЭДО. Неизвестное/legacy-состояние не позволяет выполнить поручение.
- Срок отображается по `source_due_date`, без сдвига даты часовым поясом браузера. Просрочка определяется по календарной дате в `source_timezone`; закрытые, выполненные и отменённые поручения не считаются просроченными.
- Есть фильтры всех, активных, просроченных и выполненных поручений. Отменённые записи остаются в общем списке. Пустой список, пустой фильтр, загрузка и ошибка показаны отдельно.
- Текущие права берутся из `/api/v1/organizations/current/access?application=odo`; без права выполнения остаётся чтение. Доступ и принадлежность поручения окончательно проверяются на сервере.

## Выполнение и восстановление

Пользователь вводит обязательный результат до 20000 символов Unicode. UI формирует UUID команды, сохраняет ожидаемую `source_revision` и отправляет ровно три поля: `command_id`, `expected_revision`, `result_comment`, с `Idempotency-Key: odo-command:<UUID>`. Компания/исполнитель/исходный документ не передаются из публичного UI.

Повторное нажатие блокируется синхронно до завершения запроса. При сетевой ошибке, 502/503 или ошибке сессии ЭДО результат не считается выполненным. Команда и текст остаются неизменными; пользователь может повторить тот же запрос. Данные сохраняются в sessionStorage с ключом сотрудника и компании и очищаются при выходе. Токены в журнал команд не записываются. Если browser storage отключено/переполнено, команда остаётся только в памяти до перезагрузки страницы.

При 409 UI обновляет список и требует явного создания нового запроса после получения новой revision; автоматически новый command ID не создаётся. Для 400/422 можно исправить текст и отправить новый осознанный запрос. При 403/404 показывается отказ доступа. Сырой SQL/ответ провайдера в интерфейс не выводится.

`ODO_REAUTH_REQUIRED` не завершает сессию Workspace и не вызывает её бесполезное обновление: нужен вход/исправление доверия сессии в ЭДО. Остальные ошибки авторизации Workspace сохраняют прежнее поведение HTTP-клиента.

После корректного receipt ЭДО UI показывает подтверждение и ожидание синхронизации; локальные status/revision карточки не переписываются. Список обновляется автоматически. Быстрый опрос выполняется первую минуту ожидания, затем обычный интервал 30 секунд; скрытая вкладка не опрашивается. POST автоматически по таймеру не повторяется. После прихода нужной revision сохранённая подтверждённая команда удаляется.

Устаревшие GET и запросы при уходе с экрана отменяются/игнорируются. При смене компании/сотрудника предыдущая форма и данные очищаются из отображения; команды другой области не повторяются.

## Проверки и запуск

Новых зависимостей и переменных фронтенда нет. Нужен развёрнутый бэкенд задач 3–6, миграция `000020` в ЭДО и включённые `ODO_COMMANDS_ENABLED` / `ODO_WORKSPACE_COMMANDS_ENABLED`, пользовательская авторизация и sender для обновления проекции. Применение серверных настроек и production-проверка относятся к задаче 8.

- `npx tsc -b`, `npm run i18n:check`, `npm run build`.
- `node scripts/test-odo-assignments.cjs`: статусы, границы дня в часовом поясе компании, безопасные ссылки, Unicode-лимит, receipt, область журнала, восстановление команды и API/401 ЭДО.
- Проверка браузером на локальном макете API: список, readonly, пустое состояние, ошибка, RU/KK, подтверждение и синхронизация, ошибка отправки и повтор с тем же ID после перезагрузки. Проверена ширина 390 px и форма ввода результата.

Макет и скриншоты находятся только в локальной `.cache`; production-сервисы и реальные поручения при проверке не изменялись. Реальные production-токены и сеть между Workspace и ЭДО отдельно не проверялись.

## Общая проверка задачи 8

`node scripts/test-odo-integration.cjs` запускает согласованные проверки обоих бэкендов и правила UI. Нужны `TEST_MESSENGER_DATABASE_URL` отдельной одноразовой PostgreSQL и явное `ODO_TEST_DATABASE_DISPOSABLE=true`; тесты создают и удаляют свои схемы. Можно переопределить расположение репозиториев через `ODO_TEST_WORKSPACE_REPO` / `ODO_TEST_SOURCE_REPO`. Любая ошибка или пропуск теста блокирует успешный результат. Runner не развёртывает приложение и не обращается к production API.

Порядок включения, конфигурация воркера, диагностика/retry и матрица проверки развёрнутых приложений описаны в `docs/odo-assignments-rollout.md` обоих бэкендов. Доставку в UI проверять GET/refetch: подтверждение команды не подменяет обновление проекции. После переназначения старый исполнитель должен потерять карточку; completed/closed/cancelled не считаются просроченными.
